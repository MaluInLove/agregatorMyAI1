- S3-совместимый слой хранения с сохранением `var/storage` для локальной разработки; выдача результата владельцу или администратору через авторизованный маршрут либо короткоживущую S3-ссылку.
- Срок хранения файлов 90 дней: worker физически удаляет объект, но сохраняет `media_assets` и историю. В админке можно изменить срок хранения любого файла и вручную удалить только результат/WB-версию с обязательной причиной и аудитом.
- WB-обработка видео: исходник и подготовленный файл `810×1080 MP4 H.264` доступны отдельно; в чате и таблицах результаты различаются корректно.

- Экспорт: CSV для расходов и аудита с фильтром периода; экспорт фиксируется в `audit_log`; ключи и ответы провайдеров не выгружаются.

### Важные правила предметной области

- Секрет `POLZA_API_KEY` существует только на сервере и никогда не имеет префикс `NEXT_PUBLIC_`.
- До принятия Polza создаётся бронь, после принятия — окончательное списание. Если запрос не принят, бронь освобождается. Стоимость уже созданной задачи неизменна.

- Реальные файлы локальной разработки лежат в `var/storage`; Git их не хранит.
- Повторять запрос к Polza автоматически можно только для явных ответов 408, 429, 502 и 503. Сетевой обрыв и клиентский тайм-аут не повторяются автоматически.

## Если всё же переносите проект на другую машину или в иной Git-аккаунт

Этот раздел не нужен, если меняется только аккаунт Codex, а проект, PostgreSQL и `var/storage` остаются на текущем компьютере.

1. Создать **приватный** Git-репозиторий в новом аккаунте и добавить его как `origin`.
2. Перед push сохранить весь исходный код и отдельно захватить текущие незакоммиченные файлы задачи 8. В коммит включать только осмысленные файлы проекта, не локальные артефакты.
3. Не переносить через Git: `.env`, `node_modules/`, `.next/`, `var/storage/`, `.npm-cache/`, временные `~$*.docx` и `~WRL*.tmp`.
4. Каталог `.artifact-node-modules` в этом рабочем дереве содержит массовые изменения зависимостей/инструментов. Это не работа проекта: не добавлять эти изменения в коммит и не использовать их как источник кода.
5. Передать `.env` только защищённым способом (менеджер паролей или секрет-хранилище). Не вставлять секреты в новый чат, документ или Git. После переноса в другой аккаунт разумно выпустить новый ключ Polza и, если был настроен, новый токен Postmark.
6. Если надо сохранить пользователей, историю, приглашения и результаты, сделать согласованный бэкап PostgreSQL и отдельно скопировать `var/storage`; восстановить их вместе. Одного исходного кода для этих данных недостаточно.
7. Сохранить папки `outputs/`, таблицы `.xlsx`, документы этапа 0 и скриншоты: это доказательства проверок и входные материалы дизайна, а не воспроизводимые npm-зависимости.

Пример безопасной логики переноса состояния (команды выполнять только после подстановки своих путей и имени БД):

```powershell
# На старой машине: экспорт БД в защищённое место.
pg_dump --format=custom --file=ai-aggregator.backup ai_aggregator

# На новой машине: после создания пустой БД и настройки .env.
pg_restore --clean --if-exists --dbname=ai_aggregator ai-aggregator.backup
```

До восстановления остановить приложение и worker. Не публиковать дамп БД: в нём могут быть персональные данные, хеши паролей, токены сессий и история пользователей.
